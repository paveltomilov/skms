# Тест‑план MVP (SMS тренажёр)

Проект: SMS (тренажёр)  
Версия: MVP  
Планируемый релиз: 10.03.2026  

## 1. Цели
- Подтвердить работоспособность ключевых пользовательских сценариев для ролей Учитель/Ученик.
- Проверить стабильность симуляции, корректность логики и визуальных индикаторов.
- Убедиться в корректной обработке ошибок и устойчивости при сбоях сети.

## 2. Область тестирования
Включено:
- Регистрация, аутентификация, роли и доступы.
- Кабинет учителя и кабинет ученика.
- Запуск/остановка симуляции, назначение неисправностей.
- Мультиметр и измерения.
- WebSocket‑события и обновления состояния.

Исключено:
- Админ‑панель Django (серверная часть).

## 3. Роли и доступы
- Суперпользователь (Django Admin): админ‑панель, управление данными.
- Учитель: создание учеников, удаление учеников, запуск симуляций, останов симуляции, назначение неисправностей, просмотр метрик(пока моковые данные).
- Ученик: вход по выданным данным, прохождение симуляций, выполнение заданий.

## 4. Тестовое окружение
- Браузеры: Chrome (последняя).
- ОС: Windows 10/11.
- Стенд: dev/stage.
- Данные: тестовые аккаунты учителя и ученика.

## 5. Критерии входа/выхода
Вход:
- Доступен стенд, загружены тестовые данные, активен WebSocket.
Выход:
- Нет блокирующих дефектов.
- Пройдены все критичные сценарии и регресс‑пакет.

## 6. Функциональные сценарии (критичный набор)

### 6.1 Регистрация и аутентификация
1. Регистрация пользователя → роль «Учитель» назначается автоматически.
2. Вход учителя по логину/паролю.
3. Вход ученика по выданным учителем логину/паролю.
4. Выход из системы.
5. Поведение при неверных данных (ошибка, отсутствие входа).
6. Восстановление сессии при перезагрузке.

### 6.2 Роли и доступы
1. Учитель видит кабинет учителя и функциональность управления.
2. Ученик не видит функции учителя.
3. Неавторизованный пользователь не попадает в защищённые маршруты.

### 6.3 Кабинет учителя
1. Создание/удаление ученика.
2. Запуск/завершение симуляции.
3. Назначение неисправности.
4. Просмотр метрик (если есть в MVP).

### 6.4 Кабинет ученика
1. Успешный вход по выданным данным.
2. Доступ к назначенной симуляции.
3. Выполнение задания (минимальные сценарии).

### 6.5 Симуляция и схема
1. Корректный старт состояния схемы.
2. Реакция схемы на действия пользователя.
3. Ламповые индикаторы (вкл/выкл при корректных условиях).
4. Поведение при назначенных неисправностях.

### 6.6 Мультиметр
1. Переключение режимов измерения (2 режима, отлк/750AC).
2. Корректность показаний на базовых сценариях.
3. Перетаскивание щупов (DnD).

### 6.7 WebSocket и обновления
1. Получение событий обновления точек/состояния.
2. Переподключение после разрыва.
3. Корректная обработка ошибок.

## 7. Негативные сценарии
- 401/403 от API → корректная обработка.
- Потеря сети → корректная индикация/поведение.
- Некорректные данные от API → безопасная обработка.

## 8. Регресс‑набор (минимальный)
- Логин/логаут (учитель/ученик).
- Запуск/остановка симуляции.
- Назначение неисправности.
- Мультиметр: базовый режим измерения.
- Ламповые индикаторы.

## 9. Риски
- Несоответствие логики симуляции и UI‑индикаторов.
- Сбои WebSocket приводят к неконсистентному состоянию.
- Ролевые ограничения не полностью покрыты.

## 10. Примечания
- Для расширения тест‑плана добавить таблицу тест‑кейсов с шагами/ожидаемым результатом.
- При наличии автотестов оформить привязку тест‑кейсов к наборам Jest/Playwright.
